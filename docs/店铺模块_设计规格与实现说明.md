# 店铺模块 · 设计规格与实现说明

> 版本：v0.5.0-shop ｜ 范围：`pages/shop*` 共 9 个页面 + `engine/shop.js` / `engine/tasks.js` 经营闭环
> 一句话目标：把店铺从「点按钮涨数字」升级为**带约束的经营决策沙盘**——学生用有限的行动点和现金做取舍，看到可解释的因果反馈，跑完一周后被五维评分和六项任务同时检验。
> 本文是「设计」侧的正式交付物，与《教学样板 · 实现与验收说明》互为姊妹篇（前者讲关卡教学闭环，本文讲经营沙盘闭环）。

---

## 1. 审计结论：为什么要重做

改造前的店铺模块只是「占位功能」：六个子模块各自点按钮直接改数字，没有代价、没有预算、没有取舍。审计发现 3 个 P0、4 个 P1、3 个 P2。

### P0（学不到东西 / 功能不可用）

| # | 问题 | 具体表现 | 后果 |
|---|---|---|---|
| P0-1 | `service_quality` 任务**永不可达成** | 目标「解决率 ≥90% 且评分 ≥4.3」，但全站没有任何途径修改 `service.rating` | 学生无论怎么点都拿不到这项，任务系统失去可信度 |
| P0-2 | `ad_efficiency` 任务可**白送** | ACOS 判定只看 `acos ≤ 35`；不投广告时 `acos = 0` 直接达标 | 「不做事反而满分」，与教学目标完全相反 |
| P0-3 | 店铺不是决策 | 六个子模块只做「点按钮 → 数字涨」，无代价、无预算、无取舍 | 学不到「资源有限时怎么选」，与第 4/5/6/8 章的知识点脱节 |

### P1（口径打架 / 不可回溯）

| # | 问题 | 具体表现 |
|---|---|---|
| P1-1 | KPI 与决策脱节 | `shop.metrics` 是静态种子数据，改决策不改变 KPI，页面显示「假数字」 |
| P1-2 | COGS 双口径 | 结算时 `orders * 2.21` 硬编码，与 `finance.cash` 的现金口径互相打架 |
| P1-3 | 任务不可回溯 | 任务与章节知识点、关卡、能力维度都没有关联，无法回答「这项任务在练什么」 |
| P1-4 | 重复锁定可重复发奖励 | `rewardClaimed` 作用域有误，同一周重复结算会重复发金币 |

### P2（体验与稳定性）

| # | 问题 | 具体表现 |
|---|---|---|
| P2-1 | UI 是占位代码 | 六页 JS/WXML 压缩成单行、WXSS 全空（靠样式继承），按钮无禁用态 |
| P2-2 | 无幂等 / 上限保护 | `applyShopAction` 类操作无次数上限，可无限刷数值 |
| P2-3 | 存档膨胀 | 历史记录把完整 7 天快照写进存档，周数一多存档迅速变大 |

## 2. 设计目标与教学意图

### 2.1 把「操作」重构为「决策」

```
本金（12 行动点 + 现金 ¥20,000）
   ↓
在 商品力 / 流量效率 / 库存健康 / 服务口碑 / 成本结构 五类操作中取舍
   ↓
每项操作有：行动点代价 · 现金代价 · 每周次数上限 · 前置条件
   ↓
推演指标立刻反馈（可解释的因果链：改了什么 → 哪个系数变了 → 指标怎么动）
   ↓
跑 7 天经营模拟 → 结算 → 五维决策评分 → 能力证据回写
```

### 2.2 三条教学意图

1. **取舍而非堆砌**：行动点预算固定为 12 点，完整解恰好用尽。想同时把 Listing、广告、库存、服务都拉满是不可能的——学生必须回答「本周优先解决哪两个问题」。
2. **因果可见**：每个操作按钮旁边显示「周访客 2604 → 2685」这样的即时预估；店铺首页有「这些数字怎么来的」推演依据列表。学生不是盲目点按钮，而是能说出「我改主图是为了把点击率系数从 X 提到 Y」。
3. **决策有代价、结果可回溯**：补货要花真金白银并排到仓日；广告压预算能救 ACOS 但会减少付费订单；售后补偿能拉评分但要花现金。所有操作记进 `shopActionLog`，结算时回写能力证据（进「我的 → 能力评估」）与学习事件。

## 3. 经营模型：决策 → 预测指标

实现位置：`miniprogram/engine/shop.js#deriveKpis`。全部参数集中在 `MODEL`，**调数值不改逻辑**，测试直接引用 `MODEL` 校验单调性。

### 3.1 公式

```text
# --- 自然流量 ---
Listing 质量     = (标题分×0.40 + 主图分×0.35 + 五点分×0.25) / 100      # 归一化 0~1
流量系数         = 0.55 + 0.45 × Listing 质量
评分流量系数     = clamp(1 + (评分 − 4.0) × 0.5, 0.6, 1.6)
自然日访客       = floor(1700 / 7 × 流量系数 × 评分流量系数)              # 按日取整
自然周访客       = 自然日访客 × 7

# --- 转化率 ---
价格转化系数     = (16.99 ÷ 售价) ^ 1.2
评分转化系数     = clamp(1 + (评分 − 4.0) × 0.4, 0.6, 1.6)
基础自然转化率   = (0.030 + 0.030 × Listing 质量) × 价格转化系数 × 评分转化系数
库存覆盖天数     = (可售 + 在途到仓折算量) ÷ 日需求
断货风险         = clamp((14 − 覆盖天数) ÷ 14, 0, 1)
断货转化系数     = 1 − 0.35 × 断货风险
自然转化率       = 基础自然转化率 × 断货转化系数

# --- 付费流量 ---
广告结构系数     = 0.85 + 0.30 × (结构分 ÷ 100)                          # 0.85~1.15
付费日点击       = 开广告 ? floor(日预算 ÷ 竞价) : 0
付费转化率       = 自然转化率 × 广告结构系数

# --- 汇总（关键：先按日取整再成周，与 7 日模拟同源）---
自然订单         = floor(自然日访客 × 自然转化率) × 7
付费订单         = floor(付费日点击 × 付费转化率) × 7
周订单           = 自然订单 + 付费订单
周销售额         = round(周订单 × 售价)
ACOS            = 广告花费 ÷ 周销售额
货品成本 COGS    = 周订单 × 单件成本
净利             = 销售额 − COGS − 广告花费
```

### 3.2 `MODEL` 参数表

| 参数 | 值 | 含义 |
|---|---|---|
| `baseNaturalVisitors` | 1700 | 基准周自然访客 |
| `listingWeight` | title 0.4 / image 0.35 / bullet 0.25 | Listing 质量权重 |
| `baseNaturalCvr` | 0.030 | Listing 质量最低时的自然转化率 |
| `listingCvrGain` | 0.030 | Listing 质量拉满时的转化率增量 |
| `referencePrice` | 16.99 | 定价基准（与商品默认价一致） |
| `priceElasticity` | 1.2 | 售价相对基准每涨 1%，转化降 1.2% |
| `referenceRating` | 4.0 | 评分基准 |
| `ratingTrafficGain` | 0.5 | 评分每高 1 分，自然流量 +50% |
| `ratingCvrGain` | 0.4 | 评分每高 1 分，转化 +40% |
| `adsStructureBase` | 50 | 广告结构基准分 |
| `adsStructureMin` / `Max` | 0.85 / 1.15 | 结构 0 分 / 100 分时的付费转化系数 |
| `stockoutRiskDays` | 14 | 覆盖天数低于此值开始产生断货风险 |
| `stockoutCvrPenalty` | 0.35 | 断货风险拉满时最多损失 35% 转化 |
| `unitCostUSD` | 2.21 | 单件成本（¥15 ÷ 6.8） |
| `defaultDailySales` | 18 | 缺省日均需求（用于库存覆盖天数） |
| `daysPerWeek` | 7 | 经营周长度（在途到仓覆盖折算用） |
| `stockoutRedlineDays` | 2 | 断货超过该天数视为经营红线 |

### 3.3 在途到仓折算（让补货决策能被推演看见）

补货不是立即变成可售库存，而是按交期折算本周能覆盖的比例：

```js
inTransitCover = Σ 在途单.units × clamp((7 − 到仓日 + 1) / 7, 0, 1)
可覆盖件数     = 可售库存 + inTransitCover
```

**这条是打通 6/6 可达性的关键**：快递 5 天到仓，折算后本周只能覆盖 3/7，赶不上需求爬升；本地仓加急 3 天到仓才能在本周补上货（详见第 6 节）。

## 4. 推演与结算同源（本轮最关键的架构约束）

### 4.1 问题

最初 `deriveKpis` 按**周**四舍五入（`Math.round(周流量)`、`Math.round(周订单)`），而 `simulateDay` 按**天**取整（`Math.floor`）。结果同一套决策出现：

```
店铺页推演 ACOS  33.3%
跑完一周结算 ACOS 37.7%
```

学生看到「预测说达标、结算说不达标」，会直接判定系统不可信——这是 P0 级设计缺陷。

### 4.2 修复

1. `deriveKpis` 改为**先按日 `Math.floor` 取整，再 ×7**，与模拟器逐日累加的口径一致；
2. `createSimulationState` 直接把 `kpis.naturalDailyVisitors` / `naturalCvr` / `paidCvr` 传给模拟器，模拟不再独立推导转化率。

### 4.3 验证结果

| 场景 | 推演订单 | 结算订单 | 推演 ACOS | 结算 ACOS |
|---|---|---|---|---|
| 库存充足（`available = 600`，无断货） | 133 | **133** | 27.8 | 27.79 |
| 默认决策（会断货 2 天） | 91 | **70** | 49.7 | 64.66 |

无断货时推演与结算**完全一致**；默认决策的 91→70 差额正是**断货丢单 21 单**——这不是口径漂移，而是模型在诚实地告诉学生「需求在那里，是库存拖了后腿」。这条由 `tests/shop-decisions.test.js` 第 3 组断言锁定。

### 5.1 约束校验

`planAction(shop, actionId)` 是**无副作用的只读校验**，按顺序检查：

```

```

`applyAction(shop, actionId)` 先调 `planAction`，通过后**深拷贝**执行（不修改入参），并返回新的 `next` 状态与 `kpis` 推演。

## 6. 任务系统：六项任务全部可达成，且不可白送

实现位置：`miniprogram/engine/tasks.js`。每项任务都补齐了 `chapter` / `cardId` / `advice` / `targetPage`，可回溯到章节知识点与店铺子页。

| 任务 | 目标 | 方向 | 章节·知识卡 | 关联模块 |
|---|---|---|---|---|
| `ad_efficiency` | ACOS ≤ 35% **且广告带来 ≥5 单** | `acos_healthy` | 第 4 章 · K4-01 | 广告 |
| `inventory_stability` | 本周**零断货** | `eq` | 第 5 章 · K5-03 | 库存 |
| `sales_growth` | 本周至少 **100 单** | `gte` | 第 1 章 · K1-01 | Listing |
| `service_quality` | 解决率 ≥ 90% **且**评分 ≥ 4.3 | `service` | 第 6 章 · K6-04 | 订单 |
| `profit_operation` | 本周利润为正 | `gt` | 第 8 章 · K8-02 | 看板 |
| `cash_safety` | 期末现金 ≥ ¥3,000 | `gte` | 第 8 章 · K8-01 | 看板 |

### 6.1 防白送：`acos_healthy` 方向

```js
const tested = adSpend > 0 && paidOrders >= minPaidOrders(5);
completed = tested && acos <= 35;
if (!tested) note = '广告需产生至少 5 单才能计入效率';
```

不投广告 → 花费为 0 → 判定为「未计入」而非「达标」，从根上堵掉 P0-2。

### 6.2 服务任务可达性

新增 `svc_ticket`（拉解决率）、`svc_recover` / `svc_training`（拉评分）三类操作后，`service_quality` 从「永不可达成」变为可达：完整解把解决率从 78% 拉到 90%、评分从 4.1 拉到 4.34，正好压线通过。堵掉 P0-1。

### 6.3 实时阶段用推演，结算阶段用结果

`resolveSource` 的优先级（**顺序很关键**）：

```
① 当前决策的经营推演 deriveKpis      ← 改一次决策，任务进度立刻跟着动
② 轻量周模拟 simulateWeek（WeakMap 缓存） ← 补推演没有的字段（如「本周断货天数」）
③ 上一周的既成快照 shop.metrics          ← 最后兜底
```

> 曾把静态 `shop.metrics` 放在推演之前，导致改决策任务进度不变（P1-1 的直接现象），已修正。`PROJECTION_CACHE` 用 `WeakMap` 按 `shop` 对象缓存周模拟结果，避免同一对象重复跑 7 天。

## 7. 决策评分与红线

实现位置：`miniprogram/engine/shop.js#scoreDecisions` / `findRedlines` / `buildSettlementEvidence`。

### 7.1 五维加权

| 维度 | 权重 | 口径 | 能力维度回写 |
|---|---|---|---|
| 商品力 | 20% | Listing 质量（0~100） | `listing` |
| 流量效率 | 25% | ACOS 分档 | `ads` |
| 库存健康 | 25% | 断货天数 + 期末库存 | `supply` |
| 服务口碑 | 20% | 解决率 60% + 评分 40% | `service` |
| 资金安全 | 10% | 期末现金分档 | `finance` |

**流量效率分档**：≤20→100，≤30→88，≤35→76，≤45→58，≤60→40，>60→25。

**关键防白送设计**：当 `adSpend === 0` 时，流量效率**固定 45 分**（不是 100），并给出「本周没有产生广告花费，无法评估投放效率」——与任务系统的防白送规则同源。

**库存健康**：断货 0 天→100、1 天→78、2 天→55、≥3 天→25；期末库存 ≤0 再封顶 40、<20 封顶 70。

**服务口碑**：`clamp((解决率−60)/35, 0, 1)×0.6 + clamp((评分−3.5)/0.8, 0, 1)×0.4`。

**资金安全**：现金 <0→0、<2000→45、<5000→70、<12000→88、≥12000→100。

最终 `score = round(Σ 维度分 × 权重)`，分档：≥85 优秀 / ≥70 合格 / ≥60 及格 / 其余待改进。

### 7.2 红线与合规封顶

```js
REDLINE_LABEL = { cash: '期末现金为负', stockout: '断货超过 2 天' }
```

触发任一条 → `complianceErrors > 0` → 该能力维度评分**封顶 60**，不可被其他维度抵消（复用 `engine/learning.js#COMPLIANCE_CAP` 的合规硬门槛）。

### 7.3 结算 → 能力证据

`buildSettlementEvidence(shop, settlement)` 把结算折算成 `recordAbility` 载荷：

```js
{
  levelId: `shop-week-${weeks + 1}`, chapter: 0,
  dimensions: 评分 ≥55 的维度.map(ability)      // 写进哪些能力条
  knowledge:  评分 ≥60 的维度占比                // 知识覆盖
  transfer:   decision.score / 100               // 迁移（决策水平）
  reflection: 评分 ≥75 的维度占比                // 反思
  efficiency: 资金安全分 / 100                    // 效率
  complianceErrors, redlines, decisionScore, decisionLevel, weak, at
}
```

结果进入「我的 → 能力评估」，店铺经营正式接进教学闭环。

| 净利 | ¥1,337.84 | ¥1,337.84 |
| 决策评分 | — | **88 分（优秀）** |
| 达成任务 | — | **6 / 6** |

决策分维度明细：商品力 65 / 流量效率 88 / 库存健康 100 / 服务口碑 91 / 资金安全 100。唯一弱项是商品力 65 分——这是**设计意图**：12 点预算下必须取舍，把 Listing 拉满就没有点数做库存和服务。测试断言因此写成「与本周任务挂钩的 traffic / stock / service 三维 ≥70 分，弱项 ≤1 个」，而不是「零弱项」。

### 8.3 标定过程中修掉的两个建模缺口

| 缺口 | 现象 | 修复 |
|---|---|---|
| `deriveKpis` 忽略补货决策 | 12 点用尽后 `sales_growth` 仍差 2 单（98 vs 100） | 新增在途到仓折算 `inTransitCover`，并把 `daysPerWeek` 写进 `MODEL` |
| 6/6 无可达解 | 4000 次随机搜索 + 手工解最多只能达成 5/6 | 新增 `local`（本地仓加急，3 天到仓）运费档位与 `inv_reorder_local`；`sales_growth` 目标从 10 单上调到 100 单 |

## 10. 稳定性与存档

| 机制 | 做法 |
|---|---|
| 幂等 | `applyAction` 先校验后深拷贝执行，失败返回原状态不改动 |
| 次数上限 | 每项操作有 `limit`，`planAction` 与 `applyAction` 双重把关 |
| 行动点预算 | 所有模块共享同一份 `actionPoints`，耗尽后按钮全部禁用并写明原因 |
| 重复锁定不重复发奖励 | `saveShopSettlement` 用 `rewardClaimed` 作用域正确，同一周重复结算金币不变 |
| 存档不膨胀 | `settlementHistory` 只留结论行（周次/评分/订单/ACOS/断货/利润/决策分），**不带 7 天快照**；`shopActionLog` 上限 200 条；`learningEvents` 上限 300 条 |
| 旧存档迁移 | `ensureShopState` 为旧存档补齐 `actionPoints` / `decisions` / `inventory.shipments` / `weeks`，避免页面读到 `undefined` |
| 练习/正式隔离 | `mode === 'practice'` 时操作写进 `practiceState`，不污染正式存档、不发奖励、不写能力证据 |
| 决策冻结语义 | `startShopWeek` 清空 `weekSimulation`；模拟页进入时固定决策，避免中途改决策影响已跑天数 |
