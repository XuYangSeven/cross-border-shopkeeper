## 2. 已修项

### 2.1 P0 · 存档的两条静默丢失路径

审计发现两个独立缺陷，都在 `engine/state.js`：

**路径 A：读异常 → 空白档覆盖**

修复前：

```js
function load() {
  try { cache = wx.getStorageSync(KEY) || { ...DEFAULT }; }
  catch (e) { cache = { ...DEFAULT }; }   // ← 读取抛异常时静默退回空白档
  cache = migrate(cache);
}
function init() {
  load();
  if (!cache.createdAt) { cache.createdAt = Date.now(); save(); }  // ← 立刻把空白档写回去
}
```

若 `getStorageSync` 抛异常，`cache` 变成空白档 → `createdAt` 为空 → `init()` 立即落盘，
**把可能仍然躺在存储里、只是这次没读到的进度覆盖掉**。

**路径 B：写失败静默**

```js
function save() { try { wx.setStorageSync(KEY, cache); return true; } catch (e) { return false; } }
```

返回值只在自身内部使用，`state.js` 内 **19 处** `save()` 调用点无一检查它。
存储写不进去时，用户在整个使用过程中毫无察觉，退出后才发现进度没了。

**修复**（`miniprogram/engine/state.js`）：

| 措施 | 实现 |
|---|---|
| 区分「读取抛异常」与「真的没有」 | `readKey()` 返回 `{ ok, value, error }`，只有非空且是普通对象才当作可用存档 |
| 读异常时禁止自动落盘 | `init()` 与 `ensureShopState({ persist })` 都受 `saveStatus.loadFailed` 约束 |
| 留一份完好快照 | 新增 `kuajing_save_v1.bak`；启动时 + `app.onHide` 各拍一次 → 快照 ≈「上次离开时的进度」 |
| 主键损坏时自愈 | 主键不可用但快照可用 → 从快照恢复并立刻回写主键 |
| 写失败可见 | `saveStatus` 记录 `ok / failCount / lastError`，经 `state.getSaveStatus()` 暴露 |
| 让状态有人消费 | `pages/me` 新增存档健康告警面板，仅在异常时出现 |
| 顺带修掉的浅拷贝缺陷 | 原 `{ ...DEFAULT }` 会把 `DEFAULT` 的嵌套对象共享出去，改动空档即污染进程内默认模板；改用 `mergeDefaults({}, DEFAULT)` 深拷贝 |

**为什么不每写一次就镜像一份备份**：那会把每次操作的写入量翻倍。
「启动 + 切后台」两次的写入成本相同，却能把快照保持在「上次离开时」的水位，性价比更高。

**验证**：`tests/save-durability.test.js`，8 组断言覆盖 / 自愈 / 写失败可见 / 重置后快照刷新 / 深拷贝 / 快照语义。

### 2.2 P1 · tabBar 图标

`app.json` 的 4 个 Tab 只有 `pagePath` + `text`，没有 `iconPath` / `selectedIconPath`；
`miniprogram/images/` 是**空目录**——项目从建立起就没做过 Tab 图标。微信在无图标时退化为纯文字，
视觉上像未完成品。

**修复**：新增 `tools/gen-tabbar-icons.py`，按项目既有的「像素风基线」程序化生成图标：

| 项 | 值 |
|---|---|
| 逻辑画布 | 27×27，每格 ×3 放大 |
| 输出 | 81×81 透明底 RGBA PNG ×8（4 个 Tab × 2 态） |
| 未选中色 | `#9E9E9E`（= `tabBar.color`） |
| 选中色 | `#D4A934`（= `tabBar.selectedColor`） |
| 图形 | 关卡=地图旗标；店铺=遮阳棚+店身+门洞；手册=摊开的书；我的=头肩 |

用 `NEAREST` 放大保证硬边像素、不产生抗锯齿灰边。图形经目视校对过两轮——
初版的店铺图标因「遮阳棚条纹 + 左右橱窗」在 81px 下会读成汉字结构，已改为单门洞方案。

同时新增结构审计第 10 条：**四个 Tab 必须配齐两态图标且文件真实存在**，
漏配不会报错，只能靠断言兜住。

## 3. 待决项（含取舍）

### 3.1 金币有产出无消耗（P1）—— ✅ 已解决

> **已实现，见 [求助与学习经济_设计说明.md](./求助与学习经济_设计说明.md)（v0.6.0-hints）。**
> 采用的就是下面建议「提示系统」方案：三级求助（思路免费 / 线索 30 / 解析 80），
> 配套「零提示通关 ×1.5 + 连胜」的正向激励，共 105 个步骤的提示由题目字段自动派生。
> 实现过程中另发现两处连带缺陷并修掉：`spendCoins` 缺 `load()` 保护、
> `saveLearningProgress` 会丢新增字段（导致退出重进可洗掉「用过提示」记录）。
> 以下为当初的决策记录，保留备查。

金币在「我的」页作为核心数值展示，来源是关卡星级奖励与周任务奖励，**但全站没有任何消耗出口**。
证据：`config/constants.js` 定义了 `HINT_COST: 50`，`state.js` 导出了 `spendCoins()`，
两者在 `miniprogram/` 下**零调用**。`HINT_COST` 的存在说明提示系统被设计过，只是没做。

三条路可选：

| 方案 | 代价 | 效果 |
|---|---|---|
| 做提示系统 | 中（`level.js` 已足够大，还要动关卡数据） | 让金币成为「卡关时的求助资源」，激励闭环完整 |
| 做外观/称号商店 | 中（需美术资产） | 与像素风契合，但美术成本最高 |
| 暂时在「我的」页标明用途 | 低 | 诚实但不解决激励坍塌 |

建议优先级：**提示系统 > 暂标用途 > 商店**。提示系统复用现成的 `HINT_COST`，
且能顺带缓解「卡关即流失」——这是学习类应用最大的流失点。

### 3.2 `level.js` 是上帝文件（P1）

`pages/level/level.js` 单文件 1233 行，内含：

| 指标 | 数量 |
|---|---|
| `renderStep()` 里的 `case` 分支 | 44 |
| `on*` 事件处理函数 | 78 |
| `setData` 调用 | 149 |
| 配套 `level.wxml` 的 `view.type ===` 分支块 | 43（共 484 行） |

新增一个步骤类型要同时改三处：`switch` 分支、`on*Submit` 处理、WXML 分支块。
更麻烦的是 `tests/structure-audit.test.js` 第 8 条**直接断言 `levelSrc.indexOf(`case '${type}'`)`**，
把「必须写在这一个文件里」固化成了测试契约——想拆分得先改测试。

建议：抽一层「步骤渲染器注册表」，按步骤族拆成 `pages/level/steps/{listing,ads,logistics,customer,analytics,finance}.js`，
每个渲染器自注册 `{ type, render(step, ctx), submit(e, ctx) }`，主文件只保留调度与计分。
结构审计改为断言「每个步骤类型都能被某个渲染器认领」，比断言字符串更贴合意图。

**风险**：这是纯重构、行为不变，但回归面覆盖 46 关，需要 `tests/*.test.js` 全绿 + 逐章冒烟。
建议单独一轮做，不要和其他改动混在一起。

### 3.3 全站无分享能力（P2）

`onShareAppMessage` / `onShareTimeline` 全站 **0 处**。小程序最大的自然增长通道没接。
对一个「岗位模拟学习」工具，「我通关 46 关拿到 XX 称号」是天然传播点。

建议至少在 `result`（刚通关，情绪峰值）/ `me`（能力评估）/ `intro`（介绍页）三处加转发，
带 `levelId` 参数支持深链回具体关卡。

### 3.4 13 个页面无错误边界（P2）

`pages/` 下 16 个页面里，只有 `intro` / `result` / `level` 有 `try/catch`。
其余 13 个页面若 `state.get()` 或配置读取抛错，直接白屏，用户看到微信默认错误页。
`result.js` 是写得最好的一个（payload 带 TTL、`safeDecode` 兜住截断的 URL 参数），可以照抄它的防御姿势。

建议：抽一个 `utils/pageGuard.js`，各页 `onShow` 包一层，出错时降级成「页面加载失败，返回首页」而不是白屏。

### 3.5 随机事件系统已实现但从未接入（P2）

`engine/events.js` 的 `rollDaily()` 完整实现了事件池、章节难度系数、冷却、加权随机；
`config/events.js`（1800 字节）配了事件数据。但 `rollDaily` 在全站**零调用**——
这套「每日随机事件」从没进过任何界面。

对经营沙盘来说，随机事件（差评突增、竞品降价、物流延误）正是让「每周经营」有变数的关键。
但它会**动摇现有标定**：`MODEL` 参数是按确定性推演标定的，
引入随机性后 `deriveKpis`（推演）与 `simulateWeek`（结算）的「同源」契约会被打破，
6/6 任务可达性、49→88 的决策分基准都要重标，现有测试也会失败。

建议：要做就做成「推演时预告事件区间、结算时抽签」，并把随机源做成可注入的种子以便测试可复现。
这是一次产品级改动，需要单独设计一轮，不建议顺手做。

## 5. 查过但**不是**问题（避免后续重复排查）

诚实记录两项一度被我判定为缺陷、实测后推翻的：

1. **存档体积**：一度怀疑会撑爆微信 1MB/key 上限。实测重度玩家（46 关全通 + 54 张卡全收 + 100 条错题打满 + 多轮经营周）
   的存档为 **41,390 字节 ≈ 40.4 KB，占单 key 上限的 3.95%**。所有历史型数组都有上限
   （`settlementHistory` 12、`learningEvents` 300、`mistakes` 100、`ability.records` 60、`shopActionLog` 200）。
   **不是问题**。

2. **涨跌配色矛盾**：`app.wxss` 的 `.text-up` 是绿色、`.text-down` 是红色；
   而 `styles/shop-page.wxss` 的 `.kpi-d.up` 是红色、`.kpi-d.down` 是绿色。看着像互相打架，
   查证后确认是**两条不同的语义轴**：前者是「对错轴」（绿=正确/达标），后者是「涨跌轴」（红=上升，遵循中国市场惯例）。
   **不是 bug**，但类名 `text-up` / `text-down` 极易被后来者误用到涨跌场景。
   已在 `app.wxss` 加注释锁住两条轴的含义与禁用场景。

3. **`meta` 里的云同步预留字段**：`evidenceRecords` / `outbox` / `reportSnapshots` / `attempts`
   四个字段在 `DEFAULT` 中声明、在 `migrate` 中兜底，但**全站从未写入**，是为云同步预留的占位。
   其中 `evidenceRecords` 与 `ability.records` 构成一份「迁移时同步、之后不再更新」的镜像，
   属于双份真相。当前无害（体积极小），但接入云同步前应先明确取哪一份，
   否则会出现「本地看 A、云端看 B」的分歧。**暂不删**（删掉会丢设计意图），登记为技术债。
