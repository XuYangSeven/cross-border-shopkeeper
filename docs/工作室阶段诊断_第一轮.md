## 4. 为什么是「Phase 6 打磨」，而不是继续做内容或直接发布

### 4.1 继续做内容：方向错，且会放大未验证的风险

内容侧（46 关）**已按策划案全部覆盖**，V0.3 策划案要求的是「8 章 ≈ 40 关」，实际做到 46 关。
此时再加章节属于**在没有验证教学有效性的前提下扩大投入**——如果玩测证明现有 46 关的节奏、难度曲线或
反馈密度有问题，新增章节要连带返工，而返工成本随体量线性增长。

### 4.2 直接发布：违背项目的第一性目标

项目目标是「边玩边学」。**「有没有学到」这件事，目前没有任何证据支撑**：

- 46 关的难度曲线是按设计者手感定的，没有真实玩家的失败分布；
- `passScore` 70 / 迁移题 3 答 2 / 复盘三段覆盖两段——这些阈值从未被人实际撞过；
- 提示定价（线索 30 / 解析 80）的经济平衡是**模拟出来**的（`tools/simulate-coin-economy.js`），不是**玩家跑出来**的。

发布一个教学有效性未经验证的学习产品，等于把最核心的假设赌在运气上。

### 4.3 补齐工程缺口（错误边界 / 分享 / `level.js` 拆分）：顺序应在玩测之后

这三项在《优化评审_第一轮》第 6 节里被排在「下一轮建议」。从工作室视角，**它们不该排在玩测之前**：

- 玩测会产出「哪些关卡必须改」的清单。若先按当前结构做 `level.js` 拆分（1233 → 1325 行的上帝文件），
  拆分后的结构很可能与玩测暴露的真实改动面不匹配，等于拆两遍；
- 分享与错误边界属于**发布前置项**（Phase 7 的准备），当前没有可分享的成绩背书（无人通关过），
  现在接分享的收益是空的。

### 4.4 一句话

> 内容已经做完，工程已经稳定，**唯一没被验证的是「它到底教不教得会」**——
> 这正是 Phase 6 打磨存在的意义，也是唯一该现在做的事。

## 5. Phase 6 · 打磨 执行计划（草案，待用户拍板）

### 5.1 准入门（必须先过）

| # | 项 | 理由 | 负责 |
|---|---|---|---|
| G1 | 建立 git 回滚基线 | 当前仅 1 个 `Initial Commit`，20+ 文件未提交。玩测必然引发大量改动，无基线则无法对比、无法回滚 | 用户审批后执行 |
| G2 | 固定玩测版本号 | 玩测期间禁止改动数值，否则反馈不可归因 | `release-ops-lead` |

### 5.2 玩测（Playtest）设计要点

| 项 | 方案 |
|---|---|
| 轮次 | ≥3 轮（SOP 要求） |
| 第 1 轮样本 | 用户本人（唯一即时可用、且是目标用户画像：跨境物流 B 端 PM，对跨境概念有基础、对运营细节无实操） |
| 第 1 轮范围 | 第 1 章全部 + 第 2 章前 3 关（含教学闭环全链路：卡 → 操作 → 反馈 → 重试 → 迁移 → 复述 → 结果） |
| 观察项 | 单关耗时 vs `duration` 声明值；首次答错位置；提示使用时机（在哪一级、第几次尝试）；迁移/复述是否卡住；过程中是否查阅站外资料 |
| 记录形式 | 定量（耗时 / 答错次数 / 提示消耗 / 星级）+ 定性（口语化即时吐槽）双轨 |
| 通过标准 | 第 1 章无「不知道要做什么」的死点；迁移题通过率 ≥60%；单关耗时不超过声明值 1.5 倍 |

### 5.3 后续轮次（并行）

| 成员 | 任务 |
|---|---|
| `quality-lead` | 玩测方案 + 记录表 + ≥3 轮执行与报告 |
| `engineering-lead` | 性能剖析（启动耗时 / `setData` 次数 / 存档体积回归） |
| `art-director` | 美术资产审计（当前仅 8 个程序生成 Tab 图标，无其他视觉资产） |
| `audio-director` | 音频现状评估（当前全站零音频） |

## 6. 已知风险与缓解

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | 无 git 基线就开玩测 | 玩测中改动无法回滚、无法归因 | G1 准入，先提交再玩测 |
| R2 | 玩测样本 = 1 人（设计者本人） | 反馈存在「已知道答案」偏差，难度感知失真 | 第 1 轮只用于验证**流程与卡点**，不用于判定难度；第 2 轮起引入非设计者样本 |
| R3 | `level.js` 1325 行上帝文件 | 玩测后每处改动需同时改 `switch` / `on*Submit` / WXML 三处，迭代成本高 | 玩测后再定拆分方案（避免按错误假设拆）；拆分前须先改 `tests/structure-audit.test.js` 第 8 条断言 |
| R4 | 13/16 页面无错误边界 | 玩测中若白屏，会污染反馈数据（分不清是设计问题还是崩溃） | 玩测前对本次涉及的页面加最小 `try/catch` 降级 |
| R5 | 每日随机事件系统（`engine/events.js`）已实现但未接入 | 经营沙盘的「变数」缺失，玩测可能反馈「经营太确定」 | 本轮不接入；若玩测确有此反馈，单开一轮（会打破推演/结算同源契约，需重标定） |
| R6 | 项目要求「游戏 70% / 学习 30%」 | 46 关以 `card`(69) + `dialog`(55) 为主，实际配比可能偏向学习 | 玩测观察项含「读卡是否被跳过」；若跳过率高，说明配比失衡，回 Phase 2 调整章节 |
