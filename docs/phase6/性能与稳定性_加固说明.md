## 1. 目标与范围

玩测第 1 轮（第 1 章全部 + 第 2 章前 3 关）会经过 intro / map / level / result / review / me / shop 及 9 个 shop 子页。
这几页里，凡 `state.get()` 或配置读取抛错的，`onLoad` / `onShow` 会中途中断，页面停在「已创建但没渲染出内容」的状态——
用户看到的是一片**白屏**（不是微信错误页、也不是崩溃弹窗，最难定位的那种）。

若玩测中出现白屏，会被误记为「设计问题」，污染反馈数据。因此在玩测前加一层最小错误边界，并顺带做一次可复现的性能剖析。

本轮**不重构** `level.js`（1325 行 / 164 处 `setData`），只做最小加固。

### 2.1 A + B · 页面错误边界

#### 背景（可复现的现状）
16 个页面里只有 `intro` / `result` / `level` 在业务代码里写了 `try/catch`，其余 13 页（及本任务额外纳入的 `manual`）无边界。

#### 设计
`utils/pageGuard.js` 导出一个 `definePage(pageName, config)`，**只**给 `onLoad` / `onShow` 套 `try/catch`，再把配置交给全局 `Page()`：

- **只包这两个钩子**：白屏的根因是「首次渲染前抛错」。事件回调里抛错时页面已渲染，不会白屏；逐个包住所有回调风险与收益不成比例，不在本轮范围。
- **降级而非静默**：抛错时 `console.error` 留痕 + `wx.showModal('页面加载失败')`，
  确认按钮「返回首页」执行 `wx.reLaunch('/pages/intro/intro')`（引导页是全站入口，非 tabBar 页，需用 reLaunch 清栈重开）。
  弹窗不可用时退化为 toast；连 toast 都不可用时至少保证不抛出。
- **不刷屏**：同一页面实例、同一钩子只降级一次（`__guardNotified`）。
  tabBar 页每次切换都会重跑 `onShow`，否则会变成弹窗噪音、反干扰玩测观察。
- **防死循环**：首页（`intro`）自身失败时只提示、不跳首页。
- **保留精细防御**：`result.js` 的 payload TTL / `safeDecode` / 逐字段兜底原样保留，本守卫是它外面的一层安全网。

#### 覆盖页面（16 / 16）
intro、map、level、result、review、me、shop、shop-dashboard、shop-listing、shop-ads、
shop-inventory、shop-orders、shop-health、shop-simulation、shop-settlement、**manual**。

> ⚠ 任务清单列了 15 个页面，未含 `manual`。`manual` 是 tabBar 页、玩测中随时可被点到，且属评审记录的「13 个无边界页面」之一，
> 因此**一并纳入**（16/16）。如不需要，仅需回退 `manual.js` 的 1 行改动即可。

#### 验证（未新增测试文件，避免破坏「22/22」口径）
用桩在 Node 中实跑（`map.js` 的 `refresh` 内无 try/catch，用作故障注入对象），4 项断言全过：
1. 正常路径：`onShow` 正常渲染出章节，**不弹窗**；
2. 故障路径：`state.get` 抛错 → 不向外抛、弹 1 次「页面加载失败」、确认后 `reLaunch('/pages/intro/intro')`；
3. 同实例同钩子重复 `onShow` → 仍只弹 1 次；
4. 首页失败 → 不跳首页（防循环）。

#### 理由与风险
- **理由**：把「最难排查的用户侧故障」变成「一句可读的降级提示 + 一条控制台堆栈」，避免玩测数据被污染。
- **风险与代价**：
  - 包体积：新增 `utils/pageGuard.js` 未压缩 5.1 KB（打包后经 `minified` 设置可忽略，见 §3.1）。
  - 行为差异：happy path 不变（回归测试已覆盖）；边界路径从「白屏」变为「弹窗」，是预期改动。
  - 兜底范围：`onUnload` 未包（它抛错时不影响本页渲染，见 §5）。

### 2.2 C · `shopActionLog` 上限收敛（顺手修的一个真实缺陷）

#### 背景（剖析脚本发现）
评审 §5 与《店铺模块_设计规格与实现说明》均声明「`shopActionLog` 上限 200 条」。
但代码里**只有 `applyShopAction` 一条路径做了截断**；`updateShopState`（每天推进一次 `simulate_day` 会调）、
`startShopWeek`、`saveShopSettlement` 都是直接 `push`。重度玩家跑多轮经营时会**突破 200 条、无界增长**——
剖析脚本在满配场景实测到 **224 / 200**。

#### 改动
在 `state.js` 增加统一入口 `logShopAction(entry)`（内部按 200 截断），把上述 4 条写入路径全部改走它，并删除 `applyShopAction` 里重复的截断。

#### 理由与风险
- **理由**：这不是游戏数值，而是把实现口径对齐到**已声明的文档不变量**；同时消除一条无界增长路径，属稳定性范畴。
- **风险**：低。截断行为对 `applyShopAction` 完全等价；对其余 3 条路径是把「无上限」收紧到「200 条」。
  全量测试通过（`tests/shop-state.test.js` 断言的是 1 / 相等 / 0 这类小量，不受影响）。
- 现状佐证：剖析脚本的「历史型数组上限校核」由修改前的 **✗ 224/200** 变为修改后的 **✓ 200/200**。

### 2.3 D · 性能剖析脚本

`tools/profile-performance.js`（`node tools/profile-performance.js`）三部分，**确定性、可复现、不靠目测**：

1. **包体积与文件数**：递归统计 `miniprogram/`（= `miniprogramRoot`，即实际进包内容），按扩展名 / 目录分桶，对照主包 2 MB 上限。
2. **`setData` 静态调用次数**：逐页统计 `setData(` 出现次数；对 `level.js` 用正则把每处 `setData` 归属到最近的方法，给出方法级热点。
3. **存档体积回归**：用内存 `wx` 桩驱动**真实 `state` 引擎**构造重度玩家存档，量出 JSON 字节数，并校核全部历史型数组是否在上限内。

退出码：主包超 2 MB / 满配存档超 256 KB / 任一历史数组破上限 → `exit 1`。
（门槛设在「真正异常」而非「与参考值差一点」，避免误报。）

## 5. 已知未修项 / 说明

1. **`level.js` 上帝文件**：164 处 `setData`、34 个方法内多次 `setData`、44 个 `case` 分支。
   本轮按指令只做最小加固，未拆分。建议单开一轮（评审 §3.2 已给拆分方案）。
2. **`onUnload` 未包守卫**：它在离开页面时执行，抛错不影响本页渲染（不产生白屏），故未纳入本轮。
3. **`shopState` 内的快照冗余**：`saveShopSettlement` 把完整 `settlement`（含 7 天 `snapshots`）写进 `lastSettlement`，
   同时 `shopState.snapshots` 也存一份，构成双份。当前体量可控（A 场景 shopState 12 KB），**未动**，登记为技术债。
4. **错误边界覆盖面**：只覆盖「渲染入口」。事件回调、异步回调内的异常不会白屏，本轮不处理。
5. **`miniprogram/engine/hints.js` 的注释改动不属本条工作流**，归属为主理人于 P6-T2 复核时确认并修正：该文件第 166 行原注释写「L2 只卖 20 金币、L3 才卖 50」，与权威定价 `constants.HINT_TIERS`（线索 30 / 解析 80）矛盾，而同一文件第 254 行又声明「price 一律取自 `constants.HINT_TIERS`」，属自相矛盾的过期定价注释。已改为不复述数字、只指向 `constants.HINT_TIERS`。仅注释、无行为变化，**有意保留**。
6. 评审既有的待决项（随机事件接入、分享能力）不在本轮范围。
