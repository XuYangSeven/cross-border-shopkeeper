# 云服务接入说明（学习进度跨设备同步）

> 版本：第八轮（对应 `APP_VERSION` 未 bump，仍为 `0.6.0-hints`）
> 相关文件：`miniprogram/engine/sync.js`、`miniprogram/config/cloud.js`、
> `miniprogram/config/cloud.local.js`（本地私有，不入库）、
> `miniprogram/engine/state.js`、`miniprogram/pages/me/*`、`tests/cloud-sync.test.js`

---

## 1. 目标与边界

给原本「纯单机」的跨境掌柜加一层云备份：**登录后**学习进度会同步到云端，换设备能接着学。

边界（这些是设计约束，不是未完成项）：

| 约束 | 说明 |
|---|---|
| 不登录照常可用 | 云端是**加一层**，不是改成必须联网。未登录时一切走本机存档，与接入前完全一致。 |
| 云端失败不得伤害主流程 | 任何云错误只能降级为「这次没同步」。闯关、结算、金币、星级一律不感知云端。 |
| 不引入新的个人信息 | 只存学习进度与一个归属标识（`owner_id`）。不取昵称头像、不要手机号、不采集设备信息。 |

同步的是**「我的」页之外的全部学习状态**：关卡进度与星级、金币账本、错题本、能力评估、
学习游标、店铺经营状态。同步的是**不**包含：音频开关偏好（本机设备属性，走独立存储
`kuajing_audio_pref_v1`）。

## 2. 分层与接缝

```
pages/me/me.js          ← 只做「把结果翻译成界面」
        │  sync.signIn / syncNow / signOut / getStatus
        ▼
engine/sync.js          ← 只做云端：登录、拉取、上传、冲突判定
        │  state.getSyncPayload / markSynced / applySyncPayload
        ▼
engine/state.js         ← 只做本机存档（外加三个「同步书签」字段）
```

**接缝是「同步载荷」**：`state.getSyncPayload()` 返回存档的深拷贝，并**剥掉三个同步书签**
（`syncedDigest` / `lastSyncAt` / `userId`）。

为什么书签必须剥掉：这三个字段描述的是「**本机与云端的关系**」，不是学习进度本身，
而且每次同步都会变。若留在载荷里，摘要就会自我引用 —— 每次同步后摘要都变，于是每次都
判定「有新进度」，同步会在上传与冲突之间无限打转。

`state.onSave(listener)` 是反向的缝：存档落盘后通知同步层去抖推送。它用**监听器注册表**
而不是让 `state.js` 直接 `require('./sync')`，因为那会构成 `sync → state → sync` 的循环依赖。
监听器抛错被吞掉，不影响存档主流程。

`state.save()` 被拆成了 `persist()`（只落盘，不打 `updatedAt`、不通知）与 `notifySave()`。
`markSynced()` / `applySyncPayload()` 走 `persist` —— 它们改的是书签而不是学习进度，
若走 `save()` 会再次触发推送，形成同步套娃。

## 3. 云端数据模型

表 `public.kuajing_progress`：**一行一个用户**，`owner_id` 即主键，因此写入用 `upsert` 而非
`insert`。

| 列 | 类型 | 说明 |
|---|---|---|
| `owner_id` | `text NOT NULL DEFAULT auth.uid()` | 主键。归属由数据库默认值填，**客户端不传** |
| `payload` | `jsonb NOT NULL` | 完整同步载荷（已剥书签） |
| `payload_digest` | `text NOT NULL` | 上传时的内容摘要，用于核对 jsonb 往返是否稳定 |
| `app_version` | `text` | 写入时的 `APP_VERSION`，便于日后做跨版本迁移 |
| `client_updated_at` | `timestamptz` | 存档里那份 `meta.updatedAt` |
| `synced_at` | `timestamptz NOT NULL DEFAULT now()` | 本次同步时间（服务端时间） |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | 行首次创建时间 |

安全：RLS 已开启（`pg_class.relrowsecurity = true`），并对 `anon` / `authenticated` 授权，
四条 owner-only 策略齐备：

| 策略 | 命令 | 判定 |
|---|---|---|
| `kuajing_progress_read_own` | SELECT | `USING (owner_id = auth.uid())` |
| `kuajing_progress_insert_own` | INSERT | `WITH CHECK (owner_id = auth.uid())` |
| `kuajing_progress_update_own` | UPDATE | `USING` + `WITH CHECK` **都**写 |
| `kuajing_progress_delete_own` | DELETE | `USING (owner_id = auth.uid())` |

两个易漏点：

1. **建表与 RLS 是两道独立的门**：先 `GRANT` 到 `authenticated, anon`，再 `CREATE POLICY`。
   只建策略不授权会得到形似「策略失效」的 `42501`。
2. **UPDATE 必须同时写 `USING` 与 `WITH CHECK`**：只写 `USING` 时，用户可以把自己的行
   `UPDATE` 成别人的 `owner_id`（等于把进度送人或抢占他人行）。`WITH CHECK` 是拦这一步的。

另注：`describe_table` 返回的 `Table.RLSOn` 曾与 `list_tables` 不一致（前者 false、后者 true），
已用 `pg_class.relrowsecurity` 直查证实 **RLS 确实开启**，属展示层不一致，不是真实缺陷。

## 4. 登录

采用**微信一键登录**（未要求手机号 / 邮箱，因此不生成短信路径 —— 未请求的 SMS 会产生真实费用）。

```
wx.login()                       → code
wx.getAccountInfoSync()          → 运行期 appid
cloud.auth.signInWithWechat(code, appid)   → WorkBuddy 会话
```

两个必须遵守的点：

- **appid 取运行期值**（`wx.getAccountInfoSync().miniProgram.appId`），不硬编码、不用
  `wbapp_` 的 applicationId 顶替 —— 体验版与正式版是两个不同的小程序。
- **app 不做 jscode2session、不持 AppSecret、不把 openid 当凭据**。`code` 原样交给 SDK，
  换会话在服务端完成。

读用户数据前一律先 `cloud.auth.getSession()`。**没有**匿名登录、mock 会话、
「localStorage 里当用户」这类写法。

## 5. 同步决策表

`decideSync()` 是纯函数，也是整个模块最需要被测试锁死的一段：

| 条件 | 动作 |
|---|---|
| 云端没有这份进度 | `upload` |
| 两端摘要相同 | `none`（顺带刷新书签） |
| 无共同基线 + 本机为空 + 这台设备从没同步过 | `download`（全新安装，自动取回） |
| 无共同基线，其余情况 | `conflict`（不猜，交用户定夺） |
| 本机变、云端没变 | `upload` |
| 云端变、本机没变 | `download` |
| 两端都变 | `conflict` |

**无共同基线时绝不猜。** 猜错等于平白删掉一边的进度。所以 `conflict` 是一种正常的终态，
「我的」页会给出两个明确选项：「保留本机，覆盖云端」/「保留云端，覆盖本机」，
两个都带二次确认（不可撤销）。

### 5.1 区分「全新安装」与「刚重置存档」

这两种状态在数据上长得一样：**本机为空 + 没有同步书签**。但期望的行为相反 ——
重装应该自动取回云端，而用户刚点过「重置存档」时不该被云端悄悄填回来。

判定依据是 `lastSyncAt` 这个书签本身：它回答的是「**这台设备以前同步过没有**」，而不是
「本机现在有没有内容」。

- `everSynced = false`（重装）→ `download`
- `everSynced = true`（重置过）→ `conflict`，交用户定夺

因此 `state.reset()` 刻意**保留** `lastSyncAt`（那是一段历史事实），只清 `syncedDigest`，
且**不自动上传** —— 重置只清本机，云端备份留着，用户后悔还能取回。

### 5.2 推送

学生每答一题就会触发一次 `save()`，逐次上传会把云端打爆。因此去抖：
**停手 12 秒后才推**（`PUSH_DEBOUNCE_MS`）。一次连续学习通常只产生个位数次上传。
切后台时 `app.onHide` 调 `sync.flush()` 尽力推一次（小程序转后台后请求可能被挂起，
推不出去也不影响本机存档，下次打开会再推）。

## 6. 内容摘要与 jsonb 键序

`digestOf()` = 长度 + **两条独立 FNV-1a**（不同偏移与乘数）拼成 64 位量级的指纹。
双通道是为了压低碰撞概率：单条 32 位在几万字符的载荷上碰撞并非不可能，
而**一次碰撞意味着「两端内容不同却被判为一致」→ 静默丢进度**。

求摘要前先 `canonicalize()`（递归按 key 排序）。原因：云端 `payload` 是 **jsonb，
而 jsonb 不保留键序**（按长度 + 字节序规范化）。同一份进度存取一个来回，键序就和本机
不同了。若直接对 `JSON.stringify` 求摘要，每个来回都会把「内容没变」误判成「有新进度」，
同步就会永远在冲突与上传之间打转。

下载时摘要**以收到的载荷重新算一遍为准**，不直接信任 `payload_digest` 列：
两值不一致说明 jsonb 往返真的改动了内容，需要留痕（`digestMatched: false`）。

## 7. 界面（「我的」页）

在「能力评估」之前新增「云端同步」面板：

- **未登录**：一段说明 + 「微信一键登录」按钮 + 操作结果消息。
- **已登录**：同步状态 / 上次同步时间 / 说明 + 按钮组。
  - 有冲突：「保留本机，覆盖云端」/「保留云端，覆盖本机」二选一（带确认）。
  - 无冲突：「立即同步」+「用云端进度覆盖本机」（带确认）+「退出登录」（带确认）。

同步状态色是**第四条独立的语义轴**，刻意与既有三条轴区分开：
对错轴（`app.wxss` 的 `.text-up` / `.text-down`）、指标涨跌轴（`shop-page.wxss` 的 `.kpi-d`，
红涨绿跌）、金币收支轴（`me.wxss` 的 `.ledger-in` / `.ledger-out`）。
`.sync-state-ok` / `.sync-state-bad` / `.sync-state-idle` 均取与既有轴不同的深色口径
（`#1B6B2C` / `#B71C1C` / `#7A5D0F`），对比度 ≥ 5:1。

## 8. 小程序侧的接入细节

| 事项 | 做法与原因 |
|---|---|
| 客户端工厂 | 单一初始化处 `createMiniProgramWorkBuddyCloud({ endpoint, publishableKey, wx })`。**禁止**初始化第二个 CloudBase 客户端。 |
| endpoint 与 key | 都来自 `config/cloud.js` 加载出的 `publicConfig`，**两个都必须传**：小程序没有 Origin，SDK 没有同源回退。endpoint 是**固定网关** `https://mp-api.app.workbuddy.host`，**不是**应用自己的域名 —— 不要「纠正」成应用域名。 |
| 延迟 require | `require('@tencent-ai/workbuddy-cloud-sdk/miniprogram')` 与取 `wx` 都放在函数体内。模块加载期碰 `wx.*` 会让 node 下跑测试直接抛错。 |
| 诊断适配器 | `utils/workbuddy-cloud-diagnostics.js` 原样来自技能资产，在唯一初始化处包一层 `wx`。它在初始化时打印运行期 appid，请求失败时打印 method / url / status / code（**不含**凭据与响应体）。 |
| npm 产物 | 小程序运行时只能从 `miniprogram_npm/` 解析。本仓库不装开发者工具，故用 `tools/build-miniprogram-npm.js` 等价完成「构建 npm」，并自检产物可加载。 |
| 禁止手写请求 | 不得用 `wx.request` 直接打 `/.cloud/**`。 |

`package.json` 位于 `miniprogram/`（与 `app.json` 同级，这是 npm 构建的前置条件），
版本号仅为占位；**业务版本号的单一来源仍是 `config/constants.js` 的 `APP_VERSION`**。
`node_modules` / `package-lock.json` / `package.json` 已进 `project.config.json` 的
`packOptions.ignore`，不进上传包。

## 8.1 配置的存放与「未配置」的降级（开源后新增）

仓库是公开的，`publishableKey` 虽然按设计可以下发到客户端，但它**绑定的是某一个云环境的配额与存储**，
不该随仓库一起发出去。所以配置被拆成两层：

| 文件 | 是否入库 | 内容 |
|---|---|---|
| `config/cloud.js` | ✅ 入库 | 加载器 + 纯函数 `resolveConfig()`；**不含任何真实凭据** |
| `config/cloud.local.example.js` | ✅ 入库 | 模板，字段全为占位值 |
| `config/cloud.local.js` | ❌ 已 gitignore | 真实的 `applicationId` / `publishableKey` |

`cloud.js` 用**拼出来的路径**去 require `cloud.local`，而不是写成字面量：

```js
function loadLocalConfig() {
  try {
    const modulePath = ['./cloud', 'local'].join('.');
    return require(modulePath);
  } catch (e) { return null; }
}
```

这不是为了耍花样。微信开发者工具只对**字面量** `require` 做静态依赖分析，写成 `require('./cloud.local')`
会在文件不存在时报「找不到模块」并**中断整个小程序的构建**。而云配置本来就是「有则启用、无则单机」的
可选件 —— 不该因为别人没配它就让项目编译不过。

**未配置时的行为**（`isConfigured === false`）是一条独立的验收线：

- 不创建云端客户端、不发任何请求、不调 `wx.login`（`init()` 也跳过静默恢复会话）；
- `signIn()` / `syncNow()` / `flush()` 仍然**正常 resolve**（页面不需要 try/catch），
  返回状态 `local-only`，文案是「本机为纯单机模式，学习进度已保存在手机上」——
  用独立 status 而不是 `error`，页面才不会把正常状态渲染成红色告警；
- 「我的」页切成单机说明形态，**不放出点了必然失败的按钮**。

对应断言在 `tests/cloud-sync.test.js` 第 9 组：`resolveConfig()` 的六个分支（缺凭据 / 空白串 /
非字符串 / endpoint 缺省 / endpoint 显式指定），以及整条链路未配置时 `wx.login` 调用次数必须为 **0**。
测试用替身配置塞进 `require.cache` 后重载 `sync`，用完必须删掉这条缓存，否则后面的用例会继续拿到未配置的替身。

## 9. 测试

`tests/cloud-sync.test.js`（10 组断言）：

1. **摘要**：确定性 / 键序无关 / jsonb 免疫 / 内容敏感 / 数组有序 / 长度前缀；
2. **`isPayloadEmpty`**：8 种「其实有进度」的形态都要判非空（防误判为全新安装后覆盖云端）；
3. **决策表**：含「重装 → download」与「重置 → conflict」两条**对立**断言；
4. **错误翻译**：按 `kind` / `code` 分支，不依赖文案；
5. **书签不改载荷摘要**：防推送死循环；
6. **监听器**：`save` 通知、监听器抛错不影响落盘、`markSynced` 不通知；
7. **云端覆盖**：替换 + 书签 + `updatedAt` 沿用 + 幂等；
8. **整条链路 a–k**：未登录不发请求 / 上传 / 重装自动取回 / 本机新→传 / 云端新→取 /
   冲突不写任一边 + 双向强制 / RLS 静默过滤当失败 / 读失败不动本机 /
   登录传运行期 appid / 登录失败不留会话 / 未登录 flush 不发请求；
9. **未配置云服务的降级**：`resolveConfig()` 六个分支 + 未配置时 `wx.login` 调用次数为 0 + 面板切成单机形态；
10. **「我的」页同步面板渲染**：未登录态、已登录态、冲突态、成功文案、busy 解除、5 个 handler 存在。

替身云端按 `asJsonb` 规范化存储，以复现真实的 jsonb 键序行为；`freshModules` 必须
**成对**重载 `state` 与 `sync` —— 只重载 `state` 会让 `sync` 抓住旧 `state` 实例，
测试会假通过。

**测试必须自己注入云配置，不能依赖本机是否存在 `cloud.local.js`。**
`freshModules` 默认把「已配置」的替身塞进 `require.cache[config/cloud.js]`（必须在
require `sync` **之前**），需要未配置分支的第 9 组显式换成替身 OFF。
早期版本漏了这一步，于是**全新 clone 上全量测试会变成 22/23** —— sync 的云路径被
`local-only` 短路，而 README 却写着「clone 下来 `npm test` 全绿」。
现在有/无 `cloud.local.js` 两种情形都是 23/23。改这部分前，先按「把 `cloud.local.js`
临时改名再跑一遍 `npm test`」验证一次。

```bash
npm test                          # 全量 23 个测试文件
node tests/cloud-sync.test.js     # 仅云端同步专项
node tools/verify-ux-pass.js      # 集成闸门（含主包体积，按 packOptions.ignore 统计）
```

## 10. 未闭合项

- **真机联调未做**：本仓库无微信开发者工具，「微信登录 → 换会话 → 真实读写」这条链路
  需要真机跑一遍才算闭环。首次联调建议按下面的顺序看：
  1. 进「我的」页看到未登录面板；
  2. 点登录后控制台出现 `[WorkBuddy Cloud] initialized`（含运行期 appid）；
  3. 点「立即同步」后云端表里出现一行 `owner_id` 等于该会话 user id 的记录；
  4. 若失败，看 `[WorkBuddy Cloud] request failed` 的 status / code 定位
     （`42501` = 授权或策略问题，`42P01` = 表不存在）。
- **单设备多账号切换**：当前按「同一时刻一个登录会话」处理；切账号后 `baseDigest` 会因
  归属不同而视为无基线，进而走 `conflict` 交用户定夺。这是有意的保守行为，但未做多账号
  并存的专项测试。
- **冲突合并**：冲突目前只有「整体二选一」，没有逐字段合并。字段级合并需要引入
  每类进度的独立时间戳，属产品级改动。
